# ADR-006: HTTP API surface — versioning, routes, paging, errors, concurrency, idempotency, authentication

- **Status:** Accepted (product owner, 2026-11-16) — reconstructed from PRD v0.8 with recommendation defaults approved
- **Date:** 2026-11-16
- **Deciders:** Product owner (accepted 2026-11-16); mechanism text recovered from NFR-044, NFR-045, PLT-074, PLT-076, IDEM-02, DM-7, `06d`, library `WEB_API.md`
- **PRD references:** NFR-044, NFR-045; PLT-074, PLT-076; IDEM-02…05; DM-7, PLT-072; SEC-13, BRN-011…014; INT-052; D-1 (API-first)

## Context

NFR-044 **decides**: URL segment `/api/v1`, additive evolution within v1, breaking → `/api/v2` (**ADR-006**). NFR-045 requires the API to follow ADR-006 for **versioning, routes, paging, errors, concurrency, idempotency, and authentication**. The original ADR file was missing; this reconstruction fills the full NFR-045 surface from PRD + library defaults without contradicting D-1 or ADR-004 (identity internals).

## Decision Drivers

- API-first (D-1); OpenAPI from code (INT-052)
- Consistent errors: machine code + correlation id (PLT-074)
- Paginated lists (PLT-076); NFR-023 paginated lists
- Optimistic concurrency on editable docs (PLT-072, DM-7)
- Idempotency keys (IDEM-02…05)
- 401/403/404 policy (BRN-011…014, SEC-13)
- No stack traces / secrets in errors (SEC-23)

## Options Considered

### Option A: Header versioning (`Accept: application/vnd…v1`)
Pros: clean URI. Cons: harder to browse/debug; NFR-044 **already decided** URL segment.

### Option B: URL segment `/api/v1` **(chosen — PRD-fixed)**
Pros: explicit, cacheable, matches NFR-044 verbatim. Cons: version in path forever—accepted.

### Option C: Unversioned “additive only forever”
Pros: no clutter. Cons: cannot break; NFR-044 requires `/api/v2` path for breaking changes.

## Decision

### PRD-confirmed (NFR-044 / NFR-045)

1. **Versioning:** base path **`/api/v1`**. **Additive** changes only within v1 (new optional fields, new endpoints, new optional query params). **Breaking** changes ⇒ **`/api/v2`** (and documented deprecation window—window length is a recommendation below).
2. **Routes:** resource-oriented, plural nouns, no verbs in path for CRUD; module area prefixes allowed (e.g. `/api/v1/purchase-orders`)—exact resource names per slice ADRs/requirements.
3. **Paging:** all list endpoints **paginated** (PLT-076, NFR-023). Bounded `page`/`pageSize` or equivalent with **server-side max page size**; deterministic sort with unique tie-breaker.
4. **Errors:** single error shape (library: **`ProblemDetails` / `ValidationProblemDetails`**) with **machine-readable code** + **correlation id** (PLT-074). No stack traces, SQL, or secrets (SEC-23).
5. **Status codes:** follow standard mapping (library `WEB_API.md`): 200/201/204, 400 validation, 401 unauthenticated, 403 forbidden, **404** missing **or** branch-isolated per BRN-011…014, **409** conflict/concurrency/idempotency payload mismatch as applicable, **429** rate limit. BRN policy wins over generic REST guesses.
6. **Concurrency:** optimistic concurrency on editable documents (PLT-072); expose **ETag / `If-Match`** (or equivalent rowversion token) per DM-7; stale write ⇒ **409** (or 412 if ETag semantics used—pick one and stick to it; recommendation below: **409** with ProblemDetails `concurrencyConflict` for consistency with idempotency errors).
7. **Idempotency:** retryable state-changing endpoints accept **`Idempotency-Key`** header (IDEM-02); scope per operation type + user/client + logical resource; store request hash + response reference; same key+payload ⇒ replay; same key+different payload ⇒ **409 or 422** (IDEM-04—recommend **409** `idempotencyKeyPayloadMismatch`); concurrent same-key ⇒ single execution (IDEM-05).
8. **Authentication (HTTP presentation):** `Authorization: Bearer <access-token>` for interactive users (details of token lifecycle in **ADR-004**); **API keys** for Integration Client via **`X-Api-Key: <secret>`** (frozen with ADR-009). Unauthenticated ⇒ **401**; insufficient permission ⇒ **403** (SEC-13, BRN-013/014).
9. **OpenAPI:** generated from code (INT-052); documents auth, errors, paging, idempotency headers.

### Recommendations — require owner approval

| Choice | Recommendation |
|---|---|
| Error code style | lowercase dotted or underscore codes, e.g. `validation_failed`, `concurrency_conflict`, `idempotency_key_mismatch` |
| Correlation header | Accept/generate `X-Correlation-ID`; echo on response; propagate to logs/events (OUT-06) |
| Default page size | 20; max 100 |
| Concurrency response | **409** + ProblemDetails (single conflict story) |
| Idempotency mismatch | **409** (not 422) for same-key different-payload |
| Breaking-change policy | Keep `/api/v1` supported at least **90 days** after `/api/v2` release (not in PRD) |
| API key header | **Frozen:** `X-Api-Key: <secret>` (approved 2026-11-16) |
| Rate-limit headers | `Retry-After` on 429 |

NFR-044 already fixed `/api/v1`; the other rows are free choices within the PRD—approve to freeze them.

## Consequences

- **Positive:** One contract for all slices; OpenAPI honest; idempotency/concurrency testable by ID.
- **Negative:** Strict additive discipline required; version path is permanent.
- **Follow-up:** Error code catalogue grows per slice; keep a single `docs` or constants list when A0 implements PLT-074.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Accidental breaking change in v1 | Review checklist + contract tests in CI (NFR-061) |
| Two idempotency mismatch codes (409 vs 422) | Freeze recommendation above |
| Auth scheme split brain (JWT vs API key) | ADR-004 + ADR-009 + this ADR must document **both** in OpenAPI; single middleware pipeline with two authenticators |
