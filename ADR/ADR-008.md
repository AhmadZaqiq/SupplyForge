# ADR-008: Notifications and email adapter (fake-first)

- **Status:** Accepted (product owner, 2026-11-16) — reconstructed from PRD v0.8 with recommendation defaults approved
- **Date:** 2026-11-16
- **Deciders:** Product owner (accepted 2026-11-16); mechanism text recovered from PLT-050…052, INT-001…004, INT-030, TD-2, Q-5, `11` A0 row, NFR-043 context
- **PRD references:** PLT-050, PLT-051, PLT-052; INT-001, INT-002, INT-003, INT-030, INT-031 (structure only); TD-2; Q-5; OUT-01…03, MOD-TXN-02/03; A0 gate “notification round-trip”; PLT-071 (job retries)

## Context

A0 requires **notifications minimal** with **ADR-008** and **email adapter fake (INT-030)** (`11` A0 row; INDEX A0 notes). PLT-050 mandates in-app notifications; PLT-051 sends email via Integrations **when configured**, otherwise visible pending; PLT-052 requires async retry with **failures visible**. TD-2 / Q-5 default: **email optional; manual mark-sent OK**—avoid email dependency in A2, confirm Open-PO before B4. P1 must not depend on a real SMTP provider (D-6: fakes P1).

## Decision Drivers

- A0 gate: notification **round-trip** test
- TD-2 default in force (implement default; do not invent real-mail requirement)
- No network inside DB TXN (MOD-TXN-02); post-commit async only (MOD-TXN-03)
- INT-001 adapter + fake per external category; INT-002 outbox-fed jobs; INT-003 retry/backoff/dead-letter
- MOD-8: no broker; notifications are Platform Core domain + Integrations delivery
- PLT-044/SEC-22: redact PII/secrets in notification logs

## Options Considered

### Option A: Real SMTP required for P1
Pros: “complete” email. Cons: violates TD-2/Q-5 defaults; blocks CI and demos; not A0-minimal.

### Option B: In-app only, no email path
Pros: simplest. Cons: drops PLT-051/INT-030 structure A0 explicitly requires.

### Option C: In-app notifications + pluggable email adapter with **fake/dev sender** default **(chosen)**
Pros: satisfies PLT-050…052, INT-030, TD-2, A0 round-trip; real SMTP later without redesign. Cons: fake must still exercise queue/retry/status paths.

## Decision

### PRD-confirmed

1. **In-app notifications** (PLT-050) owned by **Platform Core**: at minimum types needed for A0 tests and later slices—approval requested, low stock, delayed shipment, payment failure, invoice-gen failure (some producers arrive later; A0 defines the **type catalogue + storage + read API**).
2. **Email path** (PLT-051): when email **is configured**, enqueue via Integrations adapter; **else** notification remains **visible pending** (manual mark-sent OK per TD-2).
3. **Async retry; failures visible** (PLT-052): delivery attempts retry with backoff (INT-003); failure state queryable (PLT-052, INT-008 health view as applicable).
4. **Never inside DB transaction** (MOD-TXN-02): domain commit writes notification row + optional outbox in same TXN; **sender runs after commit** (MOD-TXN-03, OUT-01).
5. **Adapter interface + fake** (INT-001, INT-030): P1 default fake records messages for tests/demos; real SMTP adapter optional **only if** configuration present (TD-2).
6. **Email queue when configured** (INT-030): queue is job/outbox-driven (INT-002), not fire-and-forget from request thread.
7. **Manual mark-sent** is an explicit P1 workflow (TD-2)—not a temporary hack to remove without Q-5 decision.
8. **PII:** notification payloads and logs redact secrets; email addresses handled as needed for delivery but not logged in full carelessly (PLT-044, SEC-22).

### Recommendation — requires owner approval

| Choice | Recommendation | Why |
|---|---|---|
| Notification storage | Table `Notification` (MOD-1a shared list) written via Platform Core interface | Shared-table rule |
| Delivery pipeline | Outbox/job → `IEmailSender` implementation; **FakeEmailSender** writes to in-memory/DB sink for tests; **SmtpEmailSender** gated on config | INT-001/030 |
| Config switch | `Email:Mode = Fake | Smtp | Disabled` (default **Fake** in dev, **Disabled** means pending-only) | TD-2 |
| Retry | Exponential backoff + jitter (INT-003); max attempts then **dead-letter / Failed** visible (INT-003, PLT-052) | |
| Round-trip test | Create notification → appears in in-app API → fake email sink receives message → mark-sent path works → failure injection shows Failed | A0 gate |
| Templates | Fixed minimal templates in code; **no** template engine required (PLT-053 P2) | MOD-8 / size (G-8) |
| Real SMTP in A0 | **Out of scope** unless you explicitly enable it | TD-2 |

Exact config keys and max-attempt counts are **recommendations**.

## Consequences

- **Positive:** A0 gate testable without external deps; honest pending state when email off; same code path upgrades to SMTP later.
- **Negative:** Fake must be maintained as a real adapter, not a stub that skips queue semantics.
- **Follow-up:** Q-5 Open-PO confirm before B4 whether real email is required for demo.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Fake diverges from SMTP behavior | Shared `IEmailSender` contract; integration tests on queue/retry regardless of sender |
| Notification spam types grow unbounded | Start with closed list from PLT-050 + A0 needs; extend via catalogue |
| Treating manual mark-sent as tech debt to delete | TD-2 says until Q-5—keep until PO decides |
