# ADR-001: Solution layout and leaf contract assemblies

- **Status:** Accepted (product owner, 2026-11-16) — reconstructed from PRD v0.8 with recommendation defaults approved
- **Date:** 2026-11-16
- **Deciders:** Product owner (accepted 2026-11-16); mechanism text recovered from PRD §4.1–4.2, DM-8, NFR-043 item 3
- **PRD references:** MOD-1, MOD-1a, MOD-2, MOD-5, MOD-8, MOD-10; DM-8; NFR-040; NFR-043(3); `04a` dependency kinds; project `AGENTS.md` (solution layout depends on M0 ADRs)

## Context

SupplyForge is one deployable **modular monolith** (PRD §3.1, MOD-8). The PRD requires a compile-time dependency graph (C) that references only other modules’ **public contract assemblies**, a runtime call graph (R) for in-process command/query implementations, and event subscription (E) through the outbox with **no** compile-time edge to publishers. NFR-040 architecture tests must enforce both the module C/R graph and the contract-assembly graph. DM-8 requires contract DTOs in a **per-module leaf** assembly (example: `Finance.Contracts`) and forbids a shared contracts assembly. No solution or projects exist yet; creating them without this ADR would invent layout the project rules forbid.

## Decision Drivers

- PRD modular monolith, not microservices (MOD-8, §3.1)
- Leaf contract assemblies; no shared contracts assembly (DM-8, §4.1)
- Acyclic C/R and contract graphs (MOD-5); arch tests on both (NFR-040, MOD-10)
- Table ownership MOD-1 / shared-table access MOD-1a
- Library Clean Architecture defaults are **overridden** by PRD module rules (project `AGENTS.md`, library rule 4)
- Simplest structure that A0–B4 can grow without speculative projects (G-8, MOD-8)

## Options Considered

### Option A: One project per layer (classic Clean Architecture slices)
Pros: familiar layering. Cons: conflicts with PRD module ownership; cross-module table rules become layer conventions only; arch tests map poorly to MOD-1…10.

### Option B: One project per module + one leaf contracts project per module + single API host **(chosen)**
Pros: mirrors module map; contracts stay leaf; single deployable; matches DM-8 example; testable per module. Cons: more `.csproj` files than a single project.

### Option C: Shared `Contracts` project for all modules
Pros: fewer projects. Cons: **forbidden** by DM-8 (no shared contracts assembly); creates false compile-time edges.

## Decision

**Option B.** Reconstructed as follows (folder names are **recommendations** until you accept this ADR):

### PRD-confirmed (do not re-open without a new ADR)

1. **One deployable** modular monolith; schemas are not security isolation (`04a` preamble).
2. **Dependency kinds** C / R / E exactly as §4.1: C references only public contract assemblies; contract assemblies are **leaves** (no outward references to implementations or to other contracts); R is an in-process call to a contract implementation still without table access; E is outbox-only and is **not** a compile-time dependency.
3. **No shared contracts assembly.** Each module that exposes contracts owns a leaf contracts assembly (DM-8: `Finance.Contracts`, interface owned by Finance).
4. **Intended C/R topological order:**  
   `Platform Core → Master Data → Inventory / Integrations → Procurement → Inbound → Finance → Sales → Shipping → Fulfillment`.  
   Reporting is E-only; AI (P2/P3) may depend on Reporting and Integrations.
5. **Acyclic:** module C/R graph and contract-assembly graph both have no cycles (MOD-5). Sales→Finance only via Finance credit contract assemblies; Finance→Sales only as E; Finance has **no** C/R edge to Fulfillment or Sales (`04a` §4.1).
6. **MOD-1 / MOD-1a:** modules own domain tables; the only permitted cross-module table writes are shared infra tables via Platform Core or Integrations interfaces: `OutboxMessage`, `InboxMessage`, `AuditLog`, `IdempotencyKey`, `DocumentSequence`, `Notification`, `JobRun`.
7. **Architecture tests (NFR-040)** enforce both graphs, table ownership, shared-infrastructure interface-only writes, and non-compile-time event subscriptions—not merely “does it compile.”
8. **No** microservices, Redis, RabbitMQ, MediatR, CQRS framework, or generic workflow engine by default (MOD-8); additions need a new ADR.

### Recommendation — requires owner approval (structure details not fully fixed by PRD)

| Choice | Recommendation | Why |
|---|---|---|
| Host | Single ASP.NET Core Web API host project composing modules | One deployable (§3.1); NFR-060 one Compose path |
| Module projects | `src/Modules/<Module>/` with `<Module>/`, `<Module>.Contracts/` (leaf), `<Module>.Infrastructure/` where needed | Separates contracts from implementation for arch tests |
| Naming | `SupplyForge.PlatformCore`, `SupplyForge.PlatformCore.Contracts`, … | Explicit; matches module names in `04a` |
| Shared infra | `src/Shared/` or Integrations-owned implementations for MOD-1a tables only | MOD-1a list is closed; do not put business rules there |
| Tests | `tests/<Module>.UnitTests`, `tests/<Module>.IntegrationTests`, `tests/ArchitectureTests`, `tests/ApiTests` | NFR-041, NFR-050 |
| Solution | One `.sln` at repo root | Simplest for CI (NFR-061) |

Exact folder strings and assembly names are **not** PRD text; accept or amend before creating projects.

## Consequences

- **Positive:** MOD-1…5 enforceable by tests; leaf contracts keep Sales off Finance tables; single host keeps ops simple.
- **Negative:** More projects than a monolithic single csproj; cross-module features need explicit contract or event design.
- **Follow-up:** Architecture test project is part of A0 (NFR-040). New C/R edges require MOD-10 (ADR + test update).

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Contracts grow fat and become a god-assembly | Leaf rule; contracts hold only interfaces + DTOs for that module’s public surface |
| Someone references another module’s Infrastructure | Arch tests; code review; deny project references in CI |
| Layout bikeshedding delays A0 | Owner accepts or edits the recommendation table once |

## Reassessment

Revisit if a second deployable is ever proposed (would need a new ADR and likely MOD-8 review) or if arch tests cannot express the graphs with the chosen project split.
