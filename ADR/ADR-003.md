# ADR-003: Ambient transaction, outbox atomicity, and data-access composition

- **Status:** Accepted (product owner, 2026-11-16) — reconstructed from PRD v0.8 with recommendation defaults approved
- **Date:** 2026-11-16
- **Deciders:** Product owner (accepted 2026-11-16); mechanism text recovered from PRD §4.5, NFR-043 item 5, IDEM-06, TD-10, design notes FUL-032/SHP-010
- **PRD references:** MOD-1, MOD-1a, MOD-3, MOD-TXN-01…05, OUT-01…07, IDEM-01…06; NFR-010, NFR-013, NFR-050; `04c` transaction-boundary table

## Context

NFR-043 item 5 requires an ambient-transaction ADR that explains: transaction owner/orchestrator; per-module DbContext strategy; how multiple module operations share one SQL Server transaction; how shared-infrastructure tables are accessed (MOD-1/MOD-1a); how MOD-1 ownership stays enforceable; how rollback and outbox atomicity are tested; and how integration tests reproduce production transaction behavior. MOD-TXN-01 allows only sync orchestration (R) and async outbox (E)—**no** message broker, **no** distributed transactions. IDEM-06 retention and TD-10 second-TXN shipment creation are explicitly tied to this ADR.

## Decision Drivers

- One SQL Server; one business operation = one user-visible success/fail (MOD-TXN-01)
- Outbox row commits **in the same transaction** as domain state (MOD-3, OUT-01)
- No external network inside a DB transaction (MOD-TXN-02)
- MOD-1 table ownership + MOD-1a shared tables via interfaces only
- Integration tests must use real SQL Server and the same composition (NFR-050)
- Failures of sync R deps fail the orchestrating TXN (MOD-TXN-05)

## Options Considered

### Option A: Single application-wide DbContext for all modules
Pros: trivial ambient TXN. Cons: weakens MOD-1 ownership; arch tests cannot see per-module entity boundaries; encourages cross-module table access.

### Option B: Per-module DbContext + shared ambient `DbTransaction` on one connection **(chosen)**
Pros: maps to MOD-1; still one SQL transaction for multi-module R; testable. Cons: more composition code; must carefully join contexts to the transaction.

### Option C: Process-level orchestration with compensating sagas / separate TXNs
Pros: loose coupling. Cons: violates “one TXN” rules for GR, SO confirm, dispatch TXN 1, etc.; not allowed as the default mode (MOD-TXN-01).

### Option D: Distributed transactions / MSDTC or external broker
Pros: classic enterprise. Cons: **forbidden** (MOD-TXN-01, MOD-8).

## Decision

### PRD-confirmed

1. **Modes:** only (R) synchronous orchestration in one DB transaction and (E) async outbox after commit (MOD-TXN-01). No broker, no distributed transactions.
2. **Orchestrator / owner:** the **module that owns the business operation** (per `04c` §4.5.4 “Owner” column) begins and commits the transaction. Cross-module **R** calls are in-process method calls joining that ambient transaction (MOD-TXN-04)—not distributed TXNs.
3. **No external I/O inside the DB transaction** (MOD-TXN-02). Outbox **delivery**, email, HTTP, and workers run only **after commit** (MOD-TXN-03, OUT-01).
4. **Outbox atomicity:** publisher writes `OutboxMessage` in the **same** transaction as the domain change (OUT-01, MOD-3). Rollback ⇒ no orphan outbox row and no partial domain state.
5. **Shared-infrastructure tables** (`OutboxMessage`, `InboxMessage`, `AuditLog`, `IdempotencyKey`, `DocumentSequence`, `Notification`, `JobRun`): written **only** through Platform Core or Integrations **interfaces**, inside the ambient transaction (MOD-1a). Modules never `INSERT`/`UPDATE` these tables with raw EF mappings of their own.
6. **MOD-1 enforceability:** each module’s DbContext maps only that module’s domain tables. Cross-module reads use contracts (MOD-2), not joins across module entity types. Arch tests + code review enforce project references (ADR-001, NFR-040).
7. **Sync R failure** (MOD-TXN-05): exception ⇒ orchestrating TXN fails; no half-committed multi-module state.
8. **Idempotency (IDEM-01…06):** commands accept `Idempotency-Key`; same key + same payload replays original result; same key + different payload ⇒ 409/422; concurrent same-key ⇒ exactly one execution. **Retention: 72 hours** default; **dispatch→invoice derived keys ≥ 7 days** (IDEM-06).
9. **Dispatch (TD-10, FUL-032):** TXN 1 = stock + `ShipmentDispatched` outbox; **TXN 2 after commit** = Shipping create contract, idempotent by DispatchId; retry job repeats TXN 2 only. Stock success is authoritative.
10. **Invoice generation (FIN path):** separate TXN(s) after dispatch; single `InvoiceGeneration` row unique on DispatchId (not redefined here—Finance slice).
11. **Delivery:** at-least-once; inbox dedupe by event id (OUT-02); retry/backoff/dead-letter visible (OUT-03); correlation/causation ids (OUT-06).

### Per-module DbContext strategy — recommendation (details not fully in PRD)

| Choice | Recommendation |
|---|---|
| Context model | **One `DbContext` type per module**, mapping only that module’s tables (+ read-only views it owns) |
| Single-module TXN | Normal `BeginTransaction` on that module’s context |
| Multi-module TXN (R) | Orchestrator opens a **shared** `DbConnection` + `DbTransaction`; each participating module context is configured to **use that transaction** for the duration of the operation |
| Shared infra writes | Interfaces (e.g. `IOutboxWriter`, `IAuditWriter`, `IIdempotencyStore`) receive the ambient transaction/connection from the host composition—not a second connection |
| Connection lifetime | Scoped per HTTP request / job; never share `DbContext` across threads (library rule) |
| Migrations | Per-module migration assemblies against one database; apply in controlled order (NFR-013) |

### How tests prove it — PRD-driven (NFR-050, `10` §10.1)

| Concern | Test approach |
|---|---|
| Outbox atomicity | Force domain failure after outbox insert attempt ⇒ assert **no** outbox row and no domain row |
| Rollback multi-module R | Fail a later step in GR/SO confirm TXN ⇒ all module rows rolled back |
| No external call in TXN | Fake adapter that throws if invoked during TXN; assert not called until after commit |
| Idempotency | Concurrent same-key requests ⇒ one side effect; payload mismatch ⇒ 409/422 |
| Production parity | Integration tests boot the **same** host/DI composition against a **real SQL Server** container (NFR-050)—not the in-memory provider |
| TD-10 | Fail TXN 2 ⇒ stock remains committed; retry creates shipment once |

### Recommendation — requires owner approval

| Choice | Recommendation | Why |
|---|---|---|
| Transaction API | `IDbSession` / ambient transaction abstraction owned by host or Shared infra, **not** a MediatR pipeline | MOD-8; explicit ownership |
| Isolation level | `READ COMMITTED` default (SQL Server default); stricter only with measured need | Simplest that meets P1 |
| EF second-level cache | None in P1 | Not in PRD; avoid hidden staleness |

## Consequences

- **Positive:** Matches every `04c` TXN boundary row; testable atomicity; MOD-1 stays real.
- **Negative:** Composition code for joining contexts to one transaction is non-trivial; bugs here are high severity.
- **Follow-up:** Ambient session must exist before first multi-module write (A0 infrastructure, used heavily from A1/A2).

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Deadlocks across module contexts in one TXN | Consistent lock order (orchestrator first, then dependencies in topological order); keep TXNs short; no user interaction inside TXN |
| Accidental second connection | Code review + test that asserts single connection id during multi-module TXN |
| Outbox written on wrong connection | `IOutboxWriter` takes ambient TXN only; unit-test signature |

## Reassessment

If a second database or broker is ever introduced, supersede. Revisit if performance evidence shows ambient joining is a bottleneck (measure first—G-8).
