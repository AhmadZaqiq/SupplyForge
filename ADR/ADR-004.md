# ADR-004: Identity — password hashing, tokens, lockout, and authorization-scope freshness

- **Status:** Accepted (product owner, 2026-11-16) — topic confirmed as Identity; reconstructed from PRD v0.8 with recommendation defaults approved
- **Date:** 2026-11-16
- **Deciders:** Product owner (accepted 2026-11-16); fills PRD pointers: PLT-010 “(ADR)”, SEC-02 “parameters ADR”, PLT-ROLE-5 “(ADR)”, PLT-011…013, SEC-01…05
- **PRD references:** PLT-010…013, PLT-020…024, PLT-ROLE-1…5, BRN-001…014, SEC-01…05, SEC-10…13, SEC-20, NFR-001…003; A0 gate “Sign-in”

## Context

A0’s acceptance gate requires working sign-in. The PRD mandates strong KDF hashing with parameters left to an ADR (PLT-010, SEC-02), access + refresh tokens with rotation and reuse detection (PLT-011, SEC-03), lockout and rate limits (PLT-012, SEC-04/05), password reset (PLT-013), and a rule for when branch/permission scope changes take effect (PLT-ROLE-5). NFR-043 does not assign these to another ADR number. **This ADR’s identifier was not named in the PRD**; it is proposed as M0 ADR-004 because the set ADR-001…006 is required before A0 implementation (`11` A0 row, project `AGENTS.md`).

> **Owner check:** Resolved — the owner confirmed ADR-004’s topic is identity/auth on 2026-11-16 (see `docs/Decision Register.md`, "Accepted — topic = Identity").

## Decision Drivers

- SEC-02 / PLT-010: salted strong KDF; parameters explicit
- PLT-011 / SEC-03: refresh rotation, revocation, reuse detection
- PLT-012 / SEC-04/05: lockout + rate limit
- PLT-ROLE-5: scope changes within configurable delay (default 5 min) **or** on token refresh
- BRN + SEC-13: every request re-authorizes (SEC-10); 401/403/404 policy
- Library `API_SECURITY.md`: Identity `PasswordHasher`, hashed refresh tokens, short-lived access tokens, no large permission lists in JWT
- MOD-8: no external IdP in P1 (D-13); IdP is P3 (PLT-015)

## Options Considered

### Option A: Cookie session only
Pros: simple revocation. Cons: harder for API-key-style Integration Client and mobile-ish API-first posture (D-1); PRD says access + refresh **tokens**.

### Option B: Opaque access tokens only (server-side session store)
Pros: instant revoke. Cons: extra store for every request; PRD does not require it; more load.

### Option C: Short-lived JWT access token + rotating opaque refresh token + server-side auth state **(chosen)**
Pros: matches PLT-011 language; standard for ASP.NET Core; refresh family detects reuse; access JWT validates without a DB hit while **authorization still re-checks scope** (SEC-10). Cons: access token not instantly revocable until expiry—mitigated by short TTL + permission cache TTL (PLT-ROLE-5).

### Option D: External IdP (OIDC)
Pros: enterprise features. Cons: P3 only (PLT-015, D-13).

## Decision

### PRD-confirmed

1. **Users** admin-created; email + password; **salted strong KDF** hashes (PLT-010). No plaintext passwords ever stored or logged (SEC-22, PLT-044).
2. **Access + refresh tokens** (PLT-011): refresh **rotated** on every use; revoked on logout, password change, deactivation, and **reuse detection** (SEC-03).
3. **Lockout + rate limit** on auth and sensitive endpoints (PLT-012, SEC-04, SEC-05). Failed login responses are generic (library security guidance; no user enumeration).
4. **Password reset:** expiring **single-use** link; admin reset fallback (PLT-013; Q-5 default TD-2 applies to email delivery—manual/fake path OK in P1).
5. **Authorization:** permission catalogue + role bundles + multi-role union (PLT-020); branch/warehouse scope (PLT-021, BRN); endpoint metadata deny-default (PLT-022); record-level rules (PLT-023); nested resources via parent scope (PLT-024). **Every request re-authorizes** (SEC-10).
6. **401 vs 403:** invalid/missing token ⇒ 401; authenticated without function permission on in-scope resource ⇒ 403; branch-isolated foreign resource ⇒ 404 per BRN-011…014 (not redefined here).
7. **Secrets** from environment/secret store, never in repo (SEC-20, NFR-001).
8. **No 2FA / IdP in P1** (PLT-014 P2, PLT-015 P3).

### Recommendations — require owner approval (parameters PRD left open)

| Parameter | Recommendation | Source / rationale |
|---|---|---|
| **KDF algorithm** | ASP.NET Core Identity **PBKDF2** (`PasswordHasher<TUser>`) — not custom, not SHA-256 | Library `API_SECURITY.md`; SEC-02 |
| **KDF iteration count** | Use Identity defaults for the .NET 10 runtime at implementation time; if overriding, set explicitly in options and document in this ADR’s decision log | SEC-02 “parameters ADR” |
| **Access token** | JWT, **15 minutes** TTL, HS256 or RS256 with server-held key; claims: `sub`, `email` optional, `scope`/`roles` minimal, `jti`; **no** full permission catalogue in the token | Short-lived; library guidance; PLT-020 stays server-side |
| **Refresh token** | 32+ bytes cryptographically random; **stored hashed**; TTL **14 days** absolute; **rotation every use**; token **family** id—reuse of a rotated refresh revokes the family | PLT-011, SEC-03, library |
| **Clock skew** | ±2–5 minutes configured explicitly | JWT validation hygiene |
| **Lockout** | Lock account after **5** consecutive failures for **5 minutes** (configurable) | SEC-05; values not in PRD |
| **Rate limit** | Separate limiter for login/refresh/reset: per **IP + account**, e.g. 10 attempts / 5 min ⇒ 429 | SEC-04; library |
| **PLT-ROLE-5 scope freshness** | Effective permissions = DB/cache with **TTL default 5 minutes**, **and** force reload on every **refresh-token** issuance; sensitive admin endpoints may bypass cache (always DB) | PLT-ROLE-5 text: “default 5 min or on token refresh” |
| **Password policy** | Min length 12, complexity per Identity defaults, breach-password blocklist optional P1 if cheap | Not specified in PRD; standard hygiene |
| **HTTPS** | TLS everywhere in production; local dev may use HTTP with documented exception (SEC-01) | SEC-01 |

Exact numeric parameters above are **not** PRD text. Approve or change before coding PLT-010…013.

## Consequences

- **Positive:** Clear sign-in path for A0 gate; aligns with SEC/PLT IDs; no IdP dependency.
- **Negative:** Access token TTL means permission changes may lag up to cache TTL unless forced—accepted via PLT-ROLE-5 default.
- **Follow-up:** Token key rotation runbook (SEC-20); tests named `PLT-011_*`, `SEC-03_*`, `BRN-013_*`, etc.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Weak KDF parameters | Fixed in this ADR; test vector or known Identity defaults |
| Refresh reuse not detected | Family table + tests (SEC-03) |
| Permission cache stale beyond 5 min | Document; allow config `0` = always DB for high-security deploys |
| JWT alg confusion | Allow-list algorithms; validate issuer/audience (library) |

## Reassessment

Before any IdP integration (P3) or if compliance requires shorter access TTL / step-up auth. Lockout defaults revisited if false-positive rate is high in demos.
