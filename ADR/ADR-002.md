# ADR-002: Event payload versioning and consumer-owned DTOs

- **Status:** Accepted (product owner, 2026-11-16) — reconstructed from PRD v0.8 with recommendation defaults approved
- **Date:** 2026-11-16
- **Deciders:** Product owner (accepted 2026-11-16); mechanism text recovered from PRD §4.1 (E), OUT-04…07, NFR-043 item 4
- **PRD references:** MOD-3, MOD-5, MOD-TXN-01; OUT-01…07; NFR-040; NFR-043(4); `04a` event subscription rules; `04b` event catalog

## Context

Events leave a module through the outbox and are consumed asynchronously (E). The PRD forbids consumers from referencing publisher domain assemblies or publisher event-contract assemblies. Consumers must deserialize **versioned serialized payloads** into **consumer-owned DTOs** (OUT-05). Without a fixed envelope and evolution rule, payload changes would either break consumers or force illegal compile-time coupling.

## Decision Drivers

- OUT-04/05: envelope fields and schema version; additive tolerance; breaking change ⇒ new event version
- MOD-5: E edges are not compile-time dependencies
- No broker (MOD-TXN-01, OUT-07): payload must be storable and replayable from SQL Server outbox rows
- NFR-040: arch tests must see non-compile-time event subscriptions
- At-least-once delivery ⇒ consumers must be idempotent (OUT-02, MOD-3)

## Options Considered

### Option A: Shared event contract assemblies referenced by publishers and consumers
Pros: single type. Cons: creates compile-time coupling the PRD forbids (§4.1 E).

### Option B: JSON (or equivalent) versioned envelope + consumer-owned DTOs **(chosen)**
Pros: matches OUT-04/05 and §4.1 literally; independent deploy/evolve per consumer; fits outbox storage. Cons: no compiler check across modules; needs schema tests.

### Option C: Broker-native schema registry
Pros: centralized evolution. Cons: broker forbidden (MOD-8, MOD-TXN-01).

## Decision

### PRD-confirmed

1. **Envelope** (OUT-04) for every outbox event: `eventId`, `eventType`, `version`, `occurredAt` (UTC), `correlationId`, `causationId`, `branchId` when relevant, `payload`.
2. **Schema version field** required (OUT-05). **Additive** changes tolerated within the same version. **Breaking** changes require a **new event version** (and tests).
3. **Consumer-owned DTOs:** each consumer defines its own DTO type(s) and maps from the raw payload. Consumers **must not** reference publisher domain assemblies or publisher event-contract assemblies (§4.1).
4. **Serialization format:** JSON for payload and envelope (fits .NET, readable in integration tests, no extra broker formats). Envelope is the stable integration schema.
5. **Inbox dedupe** by message/event id (`InboxMessage`) so at-least-once does not double-apply (OUT-02).
6. **In-process pub/sub after outbox delivery is allowed** (OUT-07); still no RabbitMQ/broker.
7. **Arch tests:** no project reference from consumer module → publisher module’s domain or event-contract assembly for E paths; event catalog stays the authority for who subscribes (`04b` §4.4).

### Recommendation — requires owner approval

| Choice | Recommendation | Why |
|---|---|---|
| `eventType` naming | Stable string, e.g. `inventory.stock_reserved` or `Inventory.StockReserved` — pick one style and freeze it | Avoid silent renames breaking consumers |
| Version type | Integer starting at `1`, field name `version` | Simple; OUT-05 does not prescribe semver strings |
| Payload casing | `camelCase` JSON | ASP.NET Core default |
| Mapping | Explicit mapper or `System.Text.Json` deserialize into consumer DTO — **no** shared mapper library required for P1 | MOD-8: no unnecessary packages |
| Forward-compat test | Consumer fixture: unknown extra payload properties do not fail deserialize | “Additive tolerance” operationalized |

Exact `eventType` string format is not fixed in the PRD; approve one style before first production event.

## Consequences

- **Positive:** E graph stays non-compile-time; consumers can ship independently; outbox rows are self-describing.
- **Negative:** Duplicated DTO shapes across consumers; breaking changes need dual-publish or version bump discipline.
- **Follow-up:** First real events appear in A1+ (e.g. PurchaseOrderApproved). A0 implements envelope, outbox write path, inbox dedupe, and arch test hooks only.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Silent breaking payload edits | Version bump rule + consumer tests named with requirement IDs (NFR-051) |
| eventType drift | Single catalog in code comments/tests aligned to `04b` §4.4 |
| Oversized payloads | Keep events as facts/snapshots; large documents referenced by id (consistent with DM-4 spirit) |

## Reassessment

If a future ADR introduces a broker or schema registry (would violate MOD-8 unless accepted), supersede this ADR. Revisit if dual-version fan-out becomes common before B3.
