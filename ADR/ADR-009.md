# ADR-009: API keys with scopes

- **Status:** Accepted (product owner, 2026-11-16) — reconstructed from PRD v0.8 with recommendation defaults approved
- **Date:** 2026-11-16
- **Deciders:** Product owner (accepted 2026-11-16); mechanism text recovered from INT-050, PLT-020, PLT-ROLE-1, Integration Client role (`02b`), SEC-20…22, PLT-044, `11` A0 row
- **PRD references:** INT-050 (Home: A0); PLT-020, PLT-022, PLT-024; PLT-ROLE-1; BRN-001…014 (machine clients still scoped); SEC-20, SEC-21, SEC-22; PLT-044; PLT-075 (deactivate not hard-delete); NFR-002 (object auth); A0 gate “API-key scope test”

## Context

A0 requires **API keys with scopes; revoke** (**INT-050**, ADR-009). The Integration Client role (`02b`) acts only within scopes. Keys are a second authenticator alongside user bearer tokens (ADR-004 / ADR-006). Secrets must never appear in the repo or logs (SEC-20…22, PLT-044).

## Decision Drivers

- INT-050: keys **with scopes**, **revoke**; home **A0**
- Integration Client must not act outside scopes (`02b`)
- Same permission catalogue as users where applicable (PLT-020) or a defined subset—PRD does not invent a parallel auth system
- Deny default (PLT-022); every request re-authorizes (SEC-10)
- Branch scope still applies (BRN)—API keys are not a bypass
- MOD-8: no external API-management platform in P1

## Options Considered

### Option A: Static key = full admin
Pros: trivial. Cons: violates scopes and least privilege; unacceptable.

### Option B: OAuth2 client credentials only
Pros: standard. Cons: heavier than INT-050 wording; no IdP in P1 (D-13); not required by PRD.

### Option C: Opaque API key + server-side ApiKey record + scope list + revocation **(chosen)**
Pros: matches INT-050 literally; works with ADR-006 header auth; simple revoke/disable; testable in A0. Cons: key rotation is manual unless automated later.

### Option D: JWT-shaped API keys
Pros: stateless validation. Cons: harder instant revoke; scopes still need care; not required.

## Decision

### PRD-confirmed

1. **API keys** for machine clients (Integration Client); **scoped** permissions; **revocable** (INT-050).
2. **Scopes** map onto the **permission catalogue** (PLT-020 / PLT-ROLE-1): a key receives an explicit allow-list of permission codes (or role bundles—recommendation below), **deny by default** (PLT-022).
3. **Authorization every request** (SEC-10): scope check + **branch/warehouse scope** if the key is branch-limited (BRN-001…010)—keys are **not** company-wide by accident.
4. **Nested resources** authorize via parent scope (PLT-024) the same as users.
5. **Secrets:** stored **hashed** (or encrypted with server-held key if lookup requires—recommendation: **hash for authentication, store prefix for display**); never logged/returned in full (SEC-21, PLT-044, SEC-22); never in repo (SEC-20).
6. **Revocation / deactivation:** immediate deny on next request; **deactivate, do not hard-delete** (PLT-075).
7. **OpenAPI** documents the API key scheme (INT-052 + ADR-006).
8. **Scope test is an A0 gate** (`11`).

### Recommendation — requires owner approval

| Choice | Recommendation | Why |
|---|---|---|
| Key format | `sfk_<publicId>_<secret>` or separate `Id` + `Secret`; server stores **SHA-256 (or Identity-style) hash of secret** + public id for lookup | Lookup without storing plaintext |
| Auth header | **Frozen:** `X-Api-Key: <secret>` (approved 2026-11-16; joint with ADR-006) | Avoid dual schemes |
| Scope assignment | **Permission code allow-list** on the key (finer than roles) | PLT-020 catalogue reuse |
| Expiry | Optional `ExpiresAt`; recommend **require expiry** within 365 days for new keys | Hygiene; not in PRD |
| Last-used | Store `LastUsedAt` for audit | PLT-040-adjacent |
| Rate limits | Keys subject to rate limiting like users (SEC-04 spirit) | Abuse control |
| Users vs keys | Separate auth result type but **same** authorization pipeline | SEC-10 |
| Seed | A0 creates one test key in integration tests only—not a committed secret | SEC-20 |

Header format and hash algorithm details: **header frozen as `X-Api-Key`**; hash remains Identity-style (non-reversible) per ADR-004. Remaining recommendation rows (scope allow-list, expiry, last-used) approved with ADR-009 on 2026-11-16.

## Consequences

- **Positive:** A0 scope test straightforward; consistent authz; revoke works without redeploy.
- **Negative:** Manual key issuance in P1 (no self-service portal)—acceptable for portfolio scope (A-10).
- **Follow-up:** Audit all key auth events (PLT-040); redact key material always.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Key leakage in logs/URLs | Header only; redaction tests (PLT-044) |
| Scope creep to “god key” | Review seed scopes; arch/API tests for deny |
| Branch bypass via company-wide key | Default keys to explicit scopes; BRN tests cover machine client |

## Reassessment

First external partner integration; any move to OAuth client credentials (would be a new ADR, likely P2/P3).
